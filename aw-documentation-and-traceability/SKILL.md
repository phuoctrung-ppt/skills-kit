# Documentation and Traceability

## Trigger and inputs
Use when behavior, architecture, contracts, operations, setup, or workflow state changes. Require exact accepted revisions, implementation evidence, documentation ownership, existing conventions, and target audience.

## Output and scope
Produce concise maintained documentation and links connecting requirement, decision, design/contract, task, code, test, review, release, and incident artifacts as applicable. Preserve user-authored content and ownership boundaries.

## Method
1. Identify what readers must decide or do differently after the change.
2. Update the canonical source rather than duplicating competing guidance.
3. Verify examples and commands from maintained configuration or actual runs.
4. Mark limitations, versions, and compatibility evidence accurately.
5. Check links, rendering, schema, or procedures appropriate to the format.

## Evidence, exit, and handoff
Record source revisions and documentation validation results. Exit when the intended reader can act without stale or contradictory guidance. Hand documents to their owner/reviewer; return contract or product inconsistencies to the owning role instead of resolving them editorially.
